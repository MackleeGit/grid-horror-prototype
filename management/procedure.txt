**Project Procedure: Echoes in the Dark**

---

**Purpose of This Document**

This file governs *how* we work on this project — not what the project is (see concept/), but
the process, discipline, and reasoning behind every step we take. Read this before touching
any code.

---

**1. The Core Philosophy: Learn by Building**

This project is, first and foremost, a structured exercise in learning OpenGL. The game —
"Echoes in the Dark" — is the vehicle. Every feature we implement exists to teach a specific,
concrete concept in real-time 3D graphics programming.

We do not copy-paste working solutions and move on. We understand what we are writing,
why we are writing it, and what the GPU/driver is doing in response. If a line of code
cannot be justified by the person writing it, it does not belong in the codebase yet.

This means development will be slow. That is intentional. Speed is not the goal; depth is.

---

**2. Incremental, Phase-Locked Development**

We develop in strict phases, mirroring the Implementation Roadmap in concept/basic_concept_note.txt.
No phase is started until the previous phase is fully understood and working.

    Phase 1 -- Foundation
        Concepts covered: windowing systems, OpenGL context creation, the main game loop,
        delta time, FPS camera math (view matrix, lookAt), mouse/keyboard input via GLFW.
        Deliverable: A navigable black void. You can look around and move. Nothing else.

    Phase 2 -- Level Geometry
        Concepts covered: vertex data, VBOs, VAOs, index buffers, texture mapping with
        stb_image, UV coordinates, the model matrix, and iterating a 2D grid to place
        instanced geometry.
        Deliverable: The house rendered as untextured-then-textured cube walls and a floor,
        visible in the FPS view from Phase 1.

    Phase 3 -- Shaders & Lighting
        Concepts covered: the GLSL pipeline (vertex to fragment), uniform variables, the
        MVP transform chain (Model * View * Projection), spotlight cone math (dot products,
        cosine angles), ambient vs. diffuse lighting, and passing C++ state to GLSL uniforms
        at runtime.
        Deliverable: The flashlight. Pitch darkness with a cone of light cast from the
        camera. Flickering driven by a uniform float.

    Phase 4 -- Game Logic & Collisions
        Concepts covered: AABB collision detection in (x, z) space, game state management,
        entity-component thinking at the CPU level, interaction volumes (closets, fuse items),
        and the separation of rendering logic from game logic.
        Deliverable: You cannot walk through walls. You can pick up fuses. You can hide in
        a closet.

    Phase 5 -- Entity & State Loop
        Concepts covered: enemy AI as a direction vector calculation, normalised vectors for
        movement, proximity-based game state transitions, win/loss screen rendering (basic
        state machine with enum GameState), and tying flickerFactor to entity distance.
        Deliverable: The entity hunts you. The flashlight flickers as it approaches. The
        game ends on contact.

Expansion features described in concept/mvp_adherence.txt (second floor, QTEs, noise
mechanics, 2D UI overlay) are explicitly out of scope until the five phases above are
complete and well-understood.

---

**3. The Justification Rule**

Every implementation step must be documented with a clear answer to three questions:

    (a) What OpenGL or C++ concept does this introduce?
    (b) Why is this the correct way to do it at this stage of the pipeline?
    (c) What would break, or what would be missing, if we skipped it?

These justifications live as block comments in the source code, immediately above the
relevant section. They are not optional. A comment that says "sets up the VAO" is
insufficient. A comment that explains *why* a VAO is needed before issuing a draw call --
that it tells the GPU how to interpret the raw bytes in the VBO -- is acceptable.

This practice directly serves the learning goal. Future-you (or a collaborator) should be
able to read the codebase linearly and reconstruct the entire mental model of the OpenGL
pipeline from the comments alone.

---

**4. MVP Discipline**

At every phase, we build only what is needed to satisfy that phase's deliverable. Refer to
concept/mvp_adherence.txt for the reasoning on why MVP-first is the correct approach for
a graphics engine project.

Concretely, this means:
    - No premature abstraction. A raw VBO setup lives in main.cpp until we understand it
      well enough to know what a good abstraction over it looks like.
    - No feature creep. The entity has one behaviour: walk toward the player. No patrol
      paths, no line-of-sight, no sound detection -- until Phase 5 is done.
    - No polish before function. Textures come after geometry. Lighting comes after
      textures. Game logic comes after lighting.

If an idea for a feature arrives during development and it is not on the Phase roadmap,
it goes into concept/mvp_adherence.txt under a future expansions note. It does not get
coded.

---

**5. Code Style & Repository Hygiene**

    - Language: C++17.
    - Build system: CMake. Every dependency (GLFW, GLAD, GLM, stb_image) is managed
      through CMakeLists.txt. No manual include path hacks.
    - File layout: Source files are organised by the phase that introduced them.
      Shader source lives in a /shaders directory as .vert and .frag files, not as
      raw C++ string literals after Phase 3.
    - Commits: One commit per meaningful implementation step, not per session. Commit
      messages state what was implemented and what concept it demonstrates. Example:
      "Add perspective projection matrix -- Phase 1, camera fundamentals."

---

**6. The Contract**

This project moves at the pace of understanding, not the pace of completion. The finished
game matters far less than the understanding acquired along the way. If a phase takes two
weeks because we needed to truly internalise how the GPU pipeline stages map to GLSL
in/out variables, those were two well-spent weeks.

The concept folder describes what we are building.
This file describes how we build it.
The code, and its comments, will document that we understood it.
